# Usage Planner 技术说明

面向开发者的设计与算法说明。使用方法、安装和数据来源见 [README](../README.md)。项目只有一套规划算法：`planUsagePath` → `recommendedUsagePath` → `searchResetPolicies` + `forecastFirstPlan`；网页、插件页面、MCP 和 CLI 共用同一默认规则（`DEFAULT_RECOMMENDATION_MODE`）。

## 项目与算法

项目包含**独立核心算法、CLI、MCP 服务、实验与最简本地测试页**。Node.js 20+，`npm install` 后可本地运行，MIT 协议。当前页面不考虑 Credits，也不要求填写 session 或 Fast。

页面默认给出**预测供给优先的滚动规划**：主线按置信度纳入额外 reset——某次 reset 在当时生效的正常刷新前发生的概率 ≥ 60% 才计入（最多两次），并放在“大概率已经发生”的保守时刻（条件 75% 分位），而不是最可能的那个小时。用户可点时间轴上的假设卡片改为 0、1 或 2 次，仍走同一求解器；重新计算或回到推荐时恢复自动。规则常量为 `resetAssumptionRule`（`src/reset-policy-search.js`）。按下一次补给安排日均用量。预测供给能覆盖当前用量时，禁止自动兑换备用；覆盖不了时，再比较等待和备用桥接。备用越少，兑换代价越高。策略选项集中在左侧；右侧时间轴直接呈现计算结果。页面不再提供用量滑块，规划从观察到的日均用量出发。额度、实际重置或需求变化后重新计算。

页面提供四个用量策略，库通过 `planUsagePath({usageStrategy:...})` 使用：

| `usageStrategy` | 安排方式 |
|---|---|
| `balanced`（默认，Keep pace） | 始终按当前日均用量，不调速；显示何时用完、断多久、备用何时用。计入的 reset 只补额度 |
| `maximize`（不浪费额度） | 在下一次补满（计入的 reset 或正常刷新）前刚好用完当前额度，可能高于或低于当前用量 |
| `weekdays` | 周六、周日用量为零，其余可用时间分配额度 |
| `weekend-focus` | 每个补给区间优先周末；区间内没有周末时用工作日，避免额度白白刷新 |

后三种的日均值是用满额度所需的消耗率；库可传 `dailyCapacityPercent` 限定实际工作能力，有限能力或区间没有可用工作日时保留无法消耗的额度。关闭预测只按已知补给规划；取消假设不会恢复虚拟补给。预测落空的路径仍保存在 `recommendation.fallback`。周末按调用方时区及真实夏令时日界线计算，主动休息不计为断供，休息期间剩余额度保持不变。

日历分配独立于控件，位于 `src/usage-strategy.js`。核心模拟仅为所选策略连接日历、可用时间和休息状态，因为只在页面重排会改变图形却不会改变备用选择或情景评分；默认 `balanced` 沿用原计算。状态模块统一保存偏好，漏斗仅补充零消耗但仍有额度时的水平段。新增策略的日历按一次模拟批次缓存。

页面的额度图使用薄荷色、无外轮廓的单边面积带，底边固定，上缘按真实余额下降；休息段仅画虚线。同速工作段合并显示，左侧轨道名称采用同字号单行文字。几何模块的 `shape:'area'` 只连接水平页，统一顶点、数字及补满线的位置；仅用 CSS 无法同时校准这些坐标。其他调用方默认保持对称形状，计算量仍与图段数量成正比；额度、耗尽时间与重置决策不变。

## 当前策略搜索怎样计算

网页、插件页面、MCP 与 CLI 都只调用 `planUsagePath`，它总是走同一个推荐求解器（`src/reset-policy-search.js`）；旧参数会被拒绝或忽略，无法得到另一套规则。

1. 在相同14天范围，按首次重置CDF生成64组分层事件样本；在每个样本真正发生公开重置后，按那个时刻重新生成后续重置。每一步的未再发生尾部单独保留权重，不能把未显示概率归一化掉。事件采样分辨率1小时；实际额度扣减和耗尽时间连续计算。第二条图上的条件概率不能直接当作无条件的第二次供给。
2. 枚举备用策略：主动保留，或耗尽后立即兑换／等12／24小时；另比较临期使用或保留。Keep pace 的用量始终等于当前用量，只比较备用选择；日历策略另以剩余重置时间分布的35%／50%／75%分位点作为候选规划时点。这些分位数并非“概率超过多少就一定采用”的阈值。关闭预测时只比较已知资源和临期选择。
3. 每种策略在**同一批情景**中模拟。策略只能看到当时已经发生的事件，不偷看某个样本后面什么时候重置；补给后及规划复查点可按实际状态改变下一段日均。备用兑换不重启公开发布的预测时钟；任何实际补满均重开正常7天窗口。人工保留／指定使用仍是约束。
4. 评分综合完成用量、停用、用量偏差、额度覆盖损失与期末资源。每次兑换另计 `0.65 × 100 / 剩余可用备用数 / 目标日均` 的稀缺成本，并按到期前还能利用的时间折减：最后一个备用比多个库存中的一个更值得保留。权重公开在 `resetPolicyObjective`，是产品取舍，不是训练结果。
5. 推荐主线采用按置信度计入的保守时点，并检查整条主线（含最后一次假设之后）不使用备用能否覆盖当前需求。能覆盖时不桥接，只允许在备用临期前用掉以免浪费；不能覆盖时，在同一时域比较等待、兑换和临期选择。Keep pace 每段都按当前用量，不调速；日历策略向下一次补给按日历分配，最后一次假设之后恢复所选用量。人工明确指定使用仍可覆盖自动安排。备用默认至少保留一个：多于一个时，多出来的按最早到期优先用于补断供；只剩最后一个时，只在距下次已知补给仍有 ≥ 24 小时的真实断供时才用（`LAST_BANK_MINIMUM_OUTAGE_HOURS`）。周末、工作日和用满三种日历策略未指定能力上限时，每天最多安排 100% 周额度。情景评分覆盖两周，再把每条路径按目标用量顺延到它的下一次补给，计入途中的断供；否则某个方案只因断供恰好落在评分窗口之外就显得更好。第二条 reset 曲线以计划实际假设的首次时刻为前提绘制，图与计划使用同一条件分布。

`recommendation.primary` 是明确标注假设的推荐主线；`firstAction` 与页面主线一致。`fallback` 从相同首个行动模拟预测全部落空的后果，不会凭空补额度。随机情景搜索的候选评分保留在 `selected`／`candidates`，其首个行动与落空路径另存 `robustFirstAction`／`robustFallback`；它们不是条件主线的收益证明。两次预测都不是确定补给，实际发布或未按时发布后应重新计算。

这是一种可解释的随机滚动规划近似：只保证对列出的候选和当前模型评分最优，**不声称全局最优或已校准的真实收益**。`test/reset-policy-search.test.mjs` 覆盖预测开关改变策略、两次实际供给避免提前兑换、尾部质量守恒、因果决策、固定速度预览、临期约束及64／128样本建议方向的稳定性。

核心入口让库、页面与MCP使用同一结果；搜索和路径适配分别隔离在 `reset-policy-search.js` 与 `recommended-usage-path.js`。共用事件压缩模块增加对假设补给的识别，否则页面无法呈现算法已经采用的补给；日期范围纳入减速和等待的候选上界，否则新计划可能越界。旧调用保持原策略，不增加搜索成本；启用时共用情景缓存，主线另比较至多8种备用安排。未改采集、预测模型、样式或页面控件。

页面规划状态由 `src/usage-planner-state.js` 统一管理：**动作 → 状态 → 单次计算 → 结果 → 渲染**。控件只提交调量、切换模式、切换假设等动作；唯一输入适配器负责调用核心，状态从结果同步实际生效的假设。表单草稿与计算快照隔离，调量不改变模式、预测、备用约束或日期范围；语言与缩放只重新渲染。此前滑块会清掉假设并切换算法，故必须移除页面中的分散状态与求解调用；额度模拟和MCP接口保持不变，每个有效动作仍只计算一次，不增加网络请求。

## 本地页面

运行 `npm run web`，打开 `http://127.0.0.1:4173/`。只填周额度、正常刷新倒计时、备用 reset 到期日期。每次点击计算都会通过本机 HTTP 服务刷新公开证据；切换用量或备用分支时沿用同一份证据和时钟，不反复抓取或调用 LLM。

**Keep available／细水长流**是独立目标：日均消耗不高于所选目标，并给下一次补给留余量。`availabilityMode:cautious` 按已知正常刷新计算；`optimistic` 把额外 reset 累计概率达到 80% 的时点作为提前复查点，预算为 `(现余额－余量)÷剩余天数`。80% 是明确的产品取舍，不是验证过的预测准确率。初始余量为整周额度的 5% 与现余额的 20% 中较小者；预测落空时将当时剩余额度重新分配到已知刷新，保留同样比例的应急余量。实际收到 reset 后才补满、重开七天并重算，不把预测加进库存。所有候选继续在同一组多次 reset／不发生情景中评价备用的缺额、到期与保留价值，优先避免停用。未选择此目标的旧策略不改变。

核心预算和风险事实集中在 `src/availability-goal.js`。共享求解器仅增加此目标的观察／复查分配分支，必须在模拟层连接才能确保 MCP、页面、后续补给及预测落空分支采用同一用量；其他目标继续原分支，最多仅多一次布尔判断。阶段概率的截止点也仅对此目标改为实际复查点，避免显示正常刷新前的概率冒充较早复查点的概率。`alertsEnabled` 只控制重新检查时的页面提示／MCP `actionPlan.availability.notification.shouldNotify`，不修改预算，不会注册后台任务或发送系统推送。通知标志明确带 `trigger:on-plan-check`。回归见 `test/availability-goal.test.mjs` 和 MCP／页面策略测试；未调用浏览器或付费 LLM。

SEO：部署时在服务环境设置 `PUBLIC_SITE_URL` 为实际 HTTPS 根域名（不带子路径）。服务会为首页生成 canonical、Open Graph／Twitter 分享信息和 WebApplication JSON-LD，并提供 `/robots.txt`、`/sitemap.xml`。`/guide/` 与 `/zh/guide/` 直接返回完整的英文／中文说明，互相标注 hreflang；首页页脚可进入说明。未配置域名的本地或预览实例使用 `noindex`，不生成猜测的 canonical 或 sitemap；仅复制原始 HTML 到静态主机也会保持 `noindex`，需要先接入上述服务或预渲染。指南及 SEO 路由由专属 `src/site-seo.js` 提供，HTTP 入口只连接响应并补全分享图 MIME；`src/page-metadata.js` 同步语言切换后的标题、简介和分享文案，不读取规划状态、不改算法、图表、用量或已选分支。检查：`node --test test/site-seo.test.mjs test/ui-language.test.mjs`。部署后再用正式域名验证 Search Console 并提交 sitemap。

页面明确区分：

- **绿色主线**：按当前选定状态计算的用量计划，真实耗尽后显示零额度空档。
- **橙色备用**：只在建议使用时显示日期动作；未使用的备用只显示库存数量。
- **蓝色首次／紫色第二次**：各有自己的概率曲线、累计值、最可能时刻及假设操作。只有选择对应假设，才在资源路径上补满；曲线本身不产生额度。
- **同一补给点**：只显示补给动作，不重复显示耗尽；没有补给时保留真实耗尽提示。

页面按当前或已选加量计算耗尽，选择会保留到重新计算及页面刷新。备用补满后也沿用上一段用量，直到用户单独修改后段；后段的回退按钮表示“沿用上一段”。预测开关、备用去留及48小时未重置都不能自动减量。比如40%余额、当前20%/天、4天后刷新且不用备用：2天耗尽，后面2天空档；不是把用量改成10%/天。相同用量连续段不重复显示。

页面固定横向，不提供方向切换，也不读取或保存旧的竖向设置；手机专用布局留待后续适配。图按用户当地日期每天等宽，夏令时切换日仍是一格。耗尽、兑换、正常刷新按真实时间定位；标签可换行，端点不移动。页面不读取旧本地设置里的 Credits。预测可关闭，历史不足或缓存过期时也会明确关闭。

同一次计算的日期范围固定，使用／保留备用、首次／二次发布假设、加量、预测开关及窗口缩放均不改变起止日期。`src/strategy-time-range.js` 按原始账户刷新、所有备用期限及两次预测补给确定可容纳各选项的范围；每张备用最多贡献一次后继七天刷新，只作显示边界，不推荐延迟兑换或额外消耗。页面在计算完成时保存该范围，修改输入并重新计算才更新。实际路径仍在真实耗尽或刷新处结束，不为了填满横轴拉长三角形。公共几何入口只透传显示范围并映射固定日历，必须在此连接才能同时保持日期、曲线与操作坐标一致；求解器、消耗速度、概率及七天刷新规则均不改。后台检查覆盖81种备用／发布／用量组合、真实页面事件反复切换，以及改变资源后重新建立范围。

备用只在真正未获补给的耗尽点或本轮内的到期安全时刻显示兑换操作。正常刷新／假设发布已经补满时不再提示同刻兑换；本轮既不耗尽、也不临期的远期库存，`backupChoices` 返回 `actionable:false`、`atHours:null`、`at:null`、`quotaAtDecision:null`，页面只在图外显示“本轮保留”和实际到期日，不给它伪造日期或使用按钮。`backupChoicePositions`（`src/recommended-usage-path.js`）从实际路径计算每张备用的位置，网页、库与 MCP 共用。页面忽略已失效的无操作按钮事件。

显示范围对页面的三种可选用量分别检查可能耗尽，只有实际可能需要备用或本轮临期才加入后继刷新范围；远期且用不到的库存不逐张多加七天。独立库的自动变速模式继续保留较宽的兼容边界；显式要求强制兑换的库调用仍尊重其约束。后台回归包括远期／多张远期、真实耗尽、临期覆盖、正常刷新同刻耗尽、两次发布补满、固定日期范围和本轮保留的页面交互。

页面当前参考 [Poolsuite](https://poolsuite.net/) 的复古桌面风格：浅粉桌面、奶油色窗口、薄荷绿操作与额度、浅黄备用 reset，配合细深色边框和带内嵌高光的按钮。公开样式中的颜色与语义角色集中在 `src/styles/palettes/poolsuite.css`，逐项来源记录在 `poolsuite.source.json`。视觉 CSS 为本地独立实现，不包含原站脚本、图片或字体；旧 Radix、参考图及 Founder OS 主题保留但不启用。

页面只加载一个样式入口 `src/styles/theme.css`，按顺序导入当前配色、`base.css`、Reset 组件及 `retro-desktop.css`。基础文件负责排版、布局与日期定位，视觉文件负责窗口、按钮和线条，所有实际色值集中在配色文件。准备另一套配色时只需保持角色变量并切换入口中的配色与视觉文件，不复制布局或算法。结构与编辑说明见 [样式管理](src/styles/README.md)。

`src/styles/retro-desktop.css` 使用干净底色、小圆角窗口和复古按钮，不加载纸纹或彩铅滤镜。英文品牌标题、数字输入和滑块读数使用本地开源 VT323 字体，控件中的拉丁文字和日期也使用同一字体；中文及密集说明保留系统字体。其 SIL OFL 声明位于 `public/fonts/vt323/OFL.txt`。两条预测分布统一用1.2px细线、不填充面积，第二次为虚线；额度三角使用薄荷绿填充与1.2px深色轮廓。布局继续是宽屏左侧300px输入与预测、右侧横向时间轴；顶部日期、每天等宽、真实耗尽和概率坐标不随主题变化。统一入口、来源记录和文字对比度检查读取实际启用的配色。

本次核心接入限于允许手动选择新档位并透传：原 `planUsagePath` 和 MCP 的白名单只接受1、1.1、1.2，单改页面会拒绝+30%、+50%、+100%，因此两处校验必须引用同一档位表；自动规划候选、评分与消耗模拟没有扩展。显示范围模块也从同一表枚举所有可选耗尽时间，避免新档位触发备用后越出固定日期轴。现有档位和调用参数继续兼容，新增值只在调用方显式选择时生效。日期轴针对六档与备用／预测的162种组合验证固定，新档位按真实消耗耗尽并跨补满继承；未增加自动搜索分支。

页面提供 English / 中文两种语言：首次按浏览器的语言偏好列表选择可用语言，均不支持时回退英文；手动选择保存在独立的 `codex4ever-language` 项中，优先于系统偏好。静态HTML以英文作为加载前的默认内容。`src/ui-language.js` 集中管理匹配、文本和校验提示，日期仍按用户本地时区格式化。切换只重画界面，不重新抓取、重新拟合或重算策略，输入、加量、备用去留、两次假设、概率和日期范围均保留；原始 Tibo 引文保留原文。

时间轴上的“假设首次／第二次发布”卡片是可切换的条件方案，位于保守的假设时刻；切换只改变计入的 reset 次数（0–2），不更换求解器。主线由 `forecastFirstPlan` 计算：Keep pace 始终按当前日均用量，计入的 reset 只补满额度；日历策略按日历分配到下一次补给。百分数始终表示每天消耗整周额度的多少。每一次补满（备用、额外 reset、正常刷新）都重新开始 7 天周期，这是已确认的账户行为。未计入 reset 时，卡片由 `forecastAssumptionCards`（`src/reset-forecast.js`）放在同样的保守时刻，仅用于展示和切换。

在假设时刻恢复100%，同时把正常刷新改为**该次 reset 之后168小时**；后续每一次备用、额外 reset 或正常刷新都重新开始7天周期，最近发生的 reset 覆盖旧日期。每一段都从当前额度和下一目标重新分配，不区分第几次 reset：下一已选假设之前均匀用完；若临期且未保留的备用先于当前用量的耗尽时刻，则提高该段日均，在兑换前用完旧额度。当前用量会更早耗尽时按实际耗尽时刻衔接备用；没有目标的尾段恢复**当前已选日均用量**，不会把100%均摊到正常刷新。例如第二次假设恢复100%后，下一备用在21小时后兑换，建议日均消耗为114.3%额度，兑换前归零；之后没有目标则恢复当前用量。备用保留或在当前正常刷新之后才到期时不强制加量。用量较低、正常刷新先于耗尽时保留实际余量。`forecastScenario.afterReset` 返回第一后继段实际建议的日均、`allocationTarget`、当前已选用量、耗尽点及下次正常刷新。实际发生reset后仍应按账户状态重新规划。



各段需要调整时，在线段上方统一显示绝对目标“建议日均消耗 X% 额度”，不重复一行相同目标，也不显示相对增减百分数。首段也对齐当前时刻，不在总标题重复一次。假设后的固定用量仍标“沿用”，手动选择标“自选”。手动按钮与算法建议区分：按钮主行显示“当前用量／加量10%／加量20%”，副行显示对应的绝对日均，例如20%／22%／24%每天，让用户知道这些数字如何得来；算法建议继续只给绝对目标。顶部及后段按钮共用 `renderUsageChoice`，点击协议和倍率不变；横向标签区及竖向避让为两行按钮留出空间，不改变时间坐标、求解或概率。去除补给注释中重复的“0% → 100%”、重新规划提示和重复点击说明，保留期限红字、覆盖损失及假设未兑现的后果。后台渲染和页面模块交互测试检查按钮比例与绝对值对应、线段位置与风险保留，无浏览器操作。

当前日均消耗紧邻时间轴，只显示结果、输入快照的本周剩余额度及距正常刷新剩余时间。日均用量计算公式在页面任何位置都不展示，下方注释也不保留。专属 `src/usage-consumption-summary.js` 仍使用原正常刷新时间，避免计划兑换备用后推迟的时间被误用于重算历史均值；补满100%后沿用实测值。当前消耗是观察均值，手动加量和建议是未来使用计划。每段只显示日均数值或统一的绝对目标建议。

每段还可显示“备用到期前再 reset：X%”或“正常刷新前再 reset：X%”。专属 `src/phase-reset-opportunities.js` 以该段起点尚未再次发生额外 reset 为条件，计算到下一计划补给或备用安全期限的概率 `(F(截止)-F(起点))/(1-F(起点))`，返回 `phasePlans[].nextResetOpportunity`。已经选择首次或第二次额外 reset 时，从最近一次假设事件重新计算等待间隔，因此第二次之后可以显示第三次的机会；兑换备用、正常刷新不重启 Tibo 的公开发布间隔。原始预测曲线不变，这个字段只解释风险，不产生第三次补给，也不自动改变用量。

公共入口 `usage-path-planner.js` 仅连接这个专属概率模块，让网页、库及MCP得到同一结果，避免在页面另算概率。`reset-sequence-forecast.js` 允许指定最近一次假设额外 reset，并按起点缓存，复用既有间隔、钟点和冷却模型；首次／第二次原接口的含义不变，不重复抓取或调用LLM。组件统一呈现概率，布局仅为新增一行留出空间，不改变时间坐标或漏斗斜率。针对性回归覆盖第三次机会、备用兑换不重启冷却、临近到期边界以及已选用量和真实耗尽不变。

第二次额外 reset 使用独立的条件更新分布：`src/reset-sequence-forecast.js` 计算 `P(T2≤t | T1=首次标记时刻)`。首次假设发生后重新从年龄0计时，复用近期等待间隔的生存函数、发布钟点权重和次日冷却规则，不沿用针对首次的旧帖子暗示。只有均值时使用明确的指数先验回退，不编造样本。每小时概率为条件CDF之差，最可能点取第二条曲线自己的最高小时窗口中心；原先“首次加均值、校准发布钟点”的参考保留为 `meanReferenceAt`，不再当曲线峰值。原始首次CDF不变。该条件分布固定首次在参考点发生，尚未对首次发生时间的不确定性积分，因此不是无条件的第二次事件概率。

预测器返回 `followingResetEstimate`，策略输出 `resetForecast.followingReset`；包含条件起点、最可能窗口概率、条件累计值、近期均值和均值参考。第二条曲线由独立的 `followingResetDistribution` / `followingResetProbabilityByHours` 提供，不把绘图采样写入MCP响应。两条曲线在同一日期轴上分行展示，各自的最高峰、竖线、动作及补满点严格对齐。标题区分“首次”和“第二次”，重要文字均有足够对比度；默认不补满，关闭预测同时隐藏两条曲线和操作。

“假设第二次发布”会同时启用首次依赖，联合计算现在到首次、首次到第二次及之后临期备用之间的建议日均用量，同一规则贯穿后续备用链。取消第二次保留首次；取消首次或关闭预测会取消后继假设。滑块保留已有假设和模式，重新计算则建立新的推荐。没有目标的尾段才恢复当前已选用量，按真实速度耗尽并显示零额度空档；不会均摊到正常刷新。库调用 `planUsagePath({...options, assumeSecondReset:true})`，默认false。`forecastScenario.assumptions` 返回两次补给及各自未发生时的资源后果，`following.selected` 表示第二次是否选择，`afterReset.sequence` 标明后继计算从第几次开始。预测不足时保持普通资源路径，不暗中预支额度。


这只是给定补给假设及可安排所需用量时的条件配置，不是已经验证的全局最优，也不保证真的会reset或能完成如此高的用量。未发生时，结果返回仍可用的备用或等待正常刷新的后果；与正常刷新重合时仅补满一次。选中假设不修改预测分布、实际输入余额或保存的手动用量。取消、关闭预测或重新计算会恢复普通路径；手动选量也退出假设。

独立库可用 `planUsagePath({...options, assumedResetCount:1})` 选择；默认false，仅增加 `forecastScenario` 建议元数据，原有路径不变。条件模式返回独立的 `phasePlans`、`decisionTree`、`milestones` 及 `strategy.method = 'conditional-uniform-quota-allocation'`。公共入口只连接专属算法模块；中央漏斗几何只映射显式假设补给和中途正常刷新，后半段的消耗、耗尽及空档由专属模块计算，普通调用的搜索和性能不变。公共时间布局只去除终点正常刷新的重复标注，并避免在“已假设发生”之后误贴首次重置未发生的概率，不能只在算法模块解决显示重复与语义冲突。回归覆盖显式选择、取消、关闭预测、临期／保留、立即兑换覆盖、正常刷新、零余额、54组资源守恒组合、9组假设后固定用量与精确耗尽／空档，以及真实页面模块交互。

发布钟点使用**全部已收录历史**的自动 reset 日，每个事件日等权，不按近期程度衰减，也不再截取最近14天或最近五次。仍按发布者日期合并同日重复公告，纯备用发放不参加；不足三个事件日时不编造钟点习惯。采用标准圆周 von Mises 核密度，浓度通过留一对数似然在22个候选值（0及1/16至64的半倍指数网格）中选择，15分钟积分网格、0.1%均匀混合防止有限样本制造绝对不可能的钟点。调带宽不代表已完成独立准确率验证，也不强制单峰或双峰。23:00和01:00不会平均成中午。`releaseClock` 返回全历史范围、样本数、等权依据及平滑参数；显示转换到观看者当地时区。

库和预测命令省略 `timeZone` 时，在调用时读取 `Intl.DateTimeFormat().resolvedOptions().timeZone`；网页读取浏览器时区。所有时间戳保持UTC ISO，日期边界及显示按所选时区计算。远程服务不能自行判断访问者时区，调用方可传 `timeZone`（例如 `Asia/Shanghai`）；MCP依次优先显式参数、`evidence.timeZone`、运行环境时区。预测命令可用 `--time-zone Asia/Shanghai`。Tibo档案的活动时区独立使用 `campaignTimeZone`，缺失时采用 `America/Los_Angeles`，不会随观看者所在地改变发布习惯。

本次时区连接只修改规划入口默认值及MCP／命令透传：直接调用库时，页面层无法覆盖入口自身的柏林默认值，因此必须在公共入口改成运行时默认值。未传参数的调用方改用当地日期边界；显式参数仍优先。纽约、上海、UTC、远程显式覆盖和CLI／MCP均有回归测试，同一预测事件的UTC时刻保持一致。

`src/reset-release-clock.js` 独立完成钟点拟合、连续风险积分与平均间隔参考点估计。必须接入核心CDF，才能让时间轴、区间及备用评分共用同一分布；只在页面挪一个钟点会与概率矛盾。历史公告不足的调用方不增加钟点偏好。该改动不解除用量约束，但可能改变预测窗口及备用选择；CDF单调、时区与夏令时、预告截止、期限和耗尽回归均有后台测试。模型仍未校准，不把“偏晚”写成早间绝不发生。

## 实时证据与本地预测

独立预测器可直接运行 `npm run predict:reset -- --live`，或用 `--input output/live-reset-evidence.json` 离线计算；`--json` 输出完整结构，结果保存到 `output/reset-prediction.json`。不需要规划工作量或操作账户。

`local-recent-intervals-v5` 将**当前 reset 间隔**与**每天的发布钟点**分开取样。有明确活动证据时，当前节奏只取该 campaign 起止范围内两端都已观察到的自动 reset 间隔（`source:campaign-intervals`），不混入活动开始前或跨越起点的旧间隔。一个完整活动间隔即可使用，但没有置信区间；尚无完整间隔时明确标记回退。没有活动证据的纯库调用仍用最近30天完整间隔，之后才回退历史；纯备用发放不参与。`sampleFrom`、`sampleTo`、`sampleCount`、`campaignEventCount` 和 `selectionReason` 可核对统计口径。

`src/reset-campaign.js` 保存独立、带来源的活动证据，不会被72小时帖子过滤丢弃。本次28天活动由 [10月4日公告](https://x.com/thsottiaux/status/2106845241357824205) 和 [10月5日 Day 1](https://x.com/thsottiaux/status/2107158998495748264) 确定；活动日为发布者时区10月5日至11月1日，结束边界为11月2日00:00（不含）。这是按 Day 1 和28天推算的活动边界，**不是承诺的 reset 时间**。原始X页面返回403，公告内容与时间来自 [公开原帖存档](https://github.com/zarazhangrui/follow-builders/blob/main/feed-x.json)，日期计数由公开Day系列记录交叉核对。没有将其他站点的 likelihood 当输入。

预测跨过活动结束后切换到非活动历史间隔，不无限延伸高频活动；没有非活动历史时保留未解释的尾部概率。活动已结束且无结束后完整间隔时回退非活动历史，有新阶段完整间隔后才使用新阶段。条件第二次／第三次预测也按各自假设reset时刻重新定位活动边界。非活动历史是回退假设，并非活动结束后节奏已获确认。页面用固定行显示活动状态、当地起止时间、间隔样本和全历史钟点口径，平均间隔的95%区间与下次事件的80%预测窗口继续分别显示。

独立库 `predictReset({campaign,...})` 接受活动元数据；档案适配器读取 `archive.campaigns`（缺省用已收录活动），传空数组可禁用活动日历。MCP `get_reset_evidence` 返回同一 `evidence.campaign`，`predict_reset` 和规划工具原样接收。核心改动只连接独立的取样与分布模块：页面无法纠正库／MCP的样本选择或条件CDF，因此必须透传活动证据，并让后继预测使用同一结束边界；不修改使用强度、真实耗尽、备用兑换或正常刷新七天的规则。全历史钟点拟合增加一次小规模留一带宽搜索，后续CDF仍按不可变预测对象缓存。

等待间隔使用正值截断的核密度混合，每个已观察间隔分散到相邻时间，带宽为 `max(1天, 1.06×样本标准差×n^(-1/5))`；混入两份等效指数先验，其均值与近期平均间隔一致。带宽和先验都是明确的、尚未校准的建模假设。这样五个稀疏样本不会因为落在第2、4天，就制造第3天突然很低的硬切分。条件生存概率为 `S(已等待+未来时长)/S(已等待)`。

发布钟点仍使用最近14天（不足三次则回退30天）的循环核密度，90分钟带宽。它连续调节上述生存风险，在15分钟网格积分；不再把一天的固定概率强行塞入当日发布时段，消除午夜及任意48小时边界的拼接突变。功能日封锁和预告截止仍是有效证据边界。自然存在每天的峰，也可能有有数据支持的多个发布钟点；未来每天“首次 reset”的概率并不必须逐日升高，累计概率才必须不下降。

`resetTimeMode` 是未来14天中平均概率密度最高的小时窗口，时间点取窗口中心。窗口按固定UTC整点划分，再转换到用户当地时间；不以点击计算的分钟为起点，否则15:34计算会制造07:04这样的伪精确时间。首尾不足一小时的窗口保留实际时长，概率为 `F(结束)-F(开始)`，密度为概率除以时长。独立预测器、页面曲线与主标记共用这些窗口，最高峰与“最可能”标记一致。`resetTimeEstimate` 保留“上次reset＋平均间隔＋常见钟点”的参考值用于兼容，但不再把均值参考当作最可能时间。v4及旧版结构仍可输入；新预测的概率值会因v5建模修正改变。该改动只涉及预测模块与其呈现，使用强度、耗尽及备用兑换规划不变；15分钟积分按预测对象缓存，不随切换用量重复计算。

此前采用近期钟点的v5公开历史逐日回放（166天、31个事件日、无帖子）中，含次日冷却的 Brier 为0.1733，不封锁次日为0.1692，简单60天频率基线为0.1543（越低越好）。末尾30天冷却为0.1710、不封锁为0.1723、频率基线为0.1466；冷却稍有改善但仍未超过基线，该切片也不是独立留出集。这些旧结果不验证本次全历史钟点及campaign取样变更。旧档案存在6组相邻活动日自动reset，不能把经验规则当永久保证。不能把平滑曲线或通过回归测试当成准确率证明。

预测器识别 Day 编号活动条目，不写死活动天数。Tibo 数据按 `America/Los_Angeles` 的活动日计算，日期输出仍可用用户本地时区。高把握的活动功能帖触发 `campaign-feature-day`：**余下活动日的 reset 发生率降到平时的 5%，过活动日午夜解除，不延续到次日**；普通功能帖不触发这个硬规则。该规则明确标注为用户指定假设，不声称是客观保证。**2026-10-23 起默认关闭**：线上没有 LLM 判断功能强弱，公开数据也缺少不含 reset 的 Day 帖子，无法回测；可用 `enforceCampaignFeatureRule:true` 打开。之后有完整 Day 帖子（X API）和 LLM 强弱分类时，先回测再决定是否按强弱调整。Day条目宣布已完成的reset先更新公开历史，再预测下一次；备用发放仍与自动恢复区分。

另一个用户指定经验约束是 `reset-next-day-cooldown`：已确认自动 reset 的活动日及整个次日，reset 发生率降到平时的 5%（`SUPPRESSED_HAZARD_FACTOR`，可用 `predictReset({suppressedHazardFactor})` 调整），第三个活动日00:00解除。两条规则都是“很不可能”而非“不可能”：设为零时历史上6组相邻活动日 reset 会被判为不可能，公开回放的 LogLoss 从 0.606 恶化到 0.869。**2026-10-23 起默认关闭**：用 Codex Resets 截至 10/23 的完整历史逐日回放（3/1–10/23，236 天、51 个事件日），reset 后次日实际再发生率为 16%（50 天中 8 次），开启冷却时模型平均只给 0.8%，关闭后为 14.8%；整体 Brier 0.1942→0.1897，LogLoss 0.6564→0.5856。机制保留，可用 `predictReset({enforceResetCooldown:true,...})` 或 `predictionFromArchive({enforceResetCooldown:true})` 打开，以比较假设，不增加页面输入。不是固定24小时，也不跟随观看者时区变化；夏令时切换仍按活动日边界计算。`hardRules` 返回上次reset、解除时刻、剩余小时及假设来源，页面换成本地时间显示冷却期限。冷却期内只用降低后的基础发生率，历史钟点、暗示和未兑现的明确预告都不能把它抬高；实际已确认的新reset仍进入历史，并从新的事件重新计算期限。纯备用发放不启动冷却，没有上次reset记录时不虚构期限。该约束在独立预测模块生效，CDF、概率曲线、预测窗口、第二次 reset 的续发模型和策略共用它；不改变已选用量或真实耗尽计算。

`intervalModel.meanIntervalConfidence` 是近期平均间隔的近似95% Student-t置信区间，假设间隔近似独立；一个样本时返回null。`nextResetWindow` 是条件模型的10%–90%下一次时间窗口，两者含义不同，都不代表已校准到真实账户。新预告在自己的截止时刻停止加成，活动硬规则优先于暗示和预告。超出一年仍无法得到的时间分位数返回null，不编造日期。

`src/live-reset-evidence.js` 是独立采集模块：

- 从 [公开 reset API](https://codex-resets.com/api/v1/resets?limit=100) 和 [状态 API](https://codex-resets.com/api/v1/status) 获取时间、类型、原始 X 链接和近期预告。只发备用和直接恢复额度严格区分；同时直接重置并发备用的记录算直接重置。
- Tibo 帖子／回复及父帖语境：配置 X API token 时直接读官方时间线；否则只用 Codex Resets 记录里附带的帖子。**不使用任何外部 likelihood、分类分数或预测算法**。读取失败不能解释为“没有消息”。
- 可选 `USAGE_PLANNER_X_BEARER_TOKEN` 直接读取 `@thsottiaux` 的 [X 用户时间线](https://docs.x.com/x-api/posts/timelines/introduction)，保留回复、排除转帖，并展开父帖。没有令牌时仍可使用公开记录与转载源；不保证完整时间线。
- 配置标准 LLM API 后用现有 `classifyTiboPosts` 分类回复与上下文；没有配置或调用失败时只采用保守的明确语句规则。模糊回复、猜测、否定不能变成已承诺的 reset。

采集优先保留提到 reset 的帖子及带相关父帖语境的回复，避免被最近几条闲聊挤出分析范围。`latestResetMention` 返回最近相关帖子／回复的时间、原帖链接、父帖和分类；它也进入预测证据，页面在关键预测数据中直接显示原文摘要、链接与解析状态。分类置信度不作为重置概率；未识别的回复不会凭空增加概率。

本地 `web`、`mcp` 和 `predict:reset` 入口读取私有 `.env.local` 中的 `USAGE_PLANNER_LLM_MODEL`、`USAGE_PLANNER_LLM_BASE_URL`、`USAGE_PLANNER_LLM_API_KEY`；进程环境优先，安装的 MCP 可通过 `USAGE_PLANNER_ENV_FILE` 指向自己的私有文件。`.env.example` 提供 Haiku 5.5 和 Anthropic 官方兼容接口示例，其他标准 `POST /v1/chat/completions` 服务仍可配置。配置文件不打包，密钥不进入浏览器、证据缓存或公开仓库。每次刷新最多分类4条新帖子、每条最多2048输出tokens，同内容按分类版本缓存；历史及帖子仍每次刷新。

`src/reset-event-time.js` 统一校验 LLM、明确语句回退和宿主信号：`resetTiming` 区分 current/historical/unknown，`resetOccurredAt` 只记录正文明确的发生时间；没有具体时刻的新完成公告使用发帖时间作为 `announcement` 口径，并保留 `reportedAt`，不伪装成精确发生时间。JSON 可为纯对象或完整代码块，前后说明及截断输出仍拒绝。采集入库与独立预测入口都必须检查同一事件时间，否则绕过采集器的调用仍会把旧事当作新reset；这两处连接不改变概率拟合或用量规划，每条只增加常数次字符串/日期检查，不增加 API 调用。缓存键包含分类版本，修复前的内存分类不会继续沿用。

配置了模型的本地 MCP 可视化刷新会分析新帖子；`get_reset_evidence` 默认仍交给宿主，显式 `classifyPosts:true` 可取得 Haiku 的分类及校验后的历史，再原样传给预测/规划工具。分类置信度始终不等于 reset 发生概率。

最近成功的证据存入被 Git 忽略的 `output/live-reset-evidence.json`。网络失败时保留缓存原日期，并显示实时／缓存／X暂缺；不把旧数据伪装成本次更新。历史缓存超过14天或不足四次时关闭预测。`src/reset-forecast.js` 将证据交给独立的本地频率／间隔／帖子模型；明确预告只影响冷却期限之后且预告仍有效的时段。概率尚未校准到个人账户，公开公告也不能替代账户实际余额。

## MCP 接入 Codex

工具：`get_usage_snapshot`（读取本机已登录账户的额度与备用 reset，只读）、`get_reset_evidence`（公开 reset 历史与 Tibo 帖子）、`plan_usage_strategy`（唯一的规划入口，总是调用 `planUsagePath`）、`open_planner`（本地可视化页面，与结果同源）、`predict_reset`（仅预测）。`plan_usage_strategy` 的 `paceMultiplier` 设定目标用量；`recommendationMode:"feedback"` 只用于比较“不计入任何 reset”的稳健方案，默认与网页相同。已移除的旧参数会被忽略。

## 验证与限制

- 回归测试覆盖资源守恒、到期、7 天重开、置信规则、备用保留规则、各入口默认规则一致，以及界面呈现不改变计算。
- 预测模型未校准。公开回放中，模型在“今天是否 reset”上不如过去 60 天频率基线；需在活动结束、数据更多后重新回测（`npm run backtest:public`）。
- 评分只覆盖两周，之后按目标用量顺延到下一次补给计入断供；不是全局最优，只在有限候选中选择。
