# 简化输入的后台数据扫测

复现：`npm run sweep`。固定本地时间为 2026-10-13 10:00，枚举周额度 0/10/25/60/100%、2/4/8 个 session、0/1/约一半 Fast、credits 0/20/80、备用 reset 有/无、正常刷新还剩 1/6 天，共 480 组。备用 reset 设为次日到期。所有模式消耗率仍是项目示例值，不是 Codex 实测值。

结果：资源与完成量边界违规 0 组；添加备用 reset 后按时完成量下降 0 组；增加 credits 后下降 0 组；增加周额度后下降 0 组。100 组有按时完成缺口，225 组计划使用备用 reset，92 组计划消耗 credits。这些是构造数据的模型一致性检查，不是现实中的推荐准确率。

扫测先发现一个搜索缺陷：默认保留 100 个候选时，一组“0% 周额度”比“10% 周额度”的按时完成量更高。手动构造的可行计划评分也高于搜索结果，证明是候选束过窄造成漏解。默认宽度增加到 500 后，同一组恢复为按时完成 4/4 个 session、花费 63 credits；480 组复跑不再出现上述资源增加却完成更少的情况。搜索仍为近似算法，不能从这些样本推断全局最优或真实账号节省率。
