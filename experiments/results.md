# 核心算法首轮实验

复现：`npm test` 与 `npm run scenarios`。场景定义为 `src/scenarios.js`，所有资源与价格为手动构造。工作单位是可分割的标准任务；这些结果不是实际账号收益，也不证明全局最优。

| 场景 | 眼前模式 / 单位每小时 | reset | 规划内 credits | 完成 / 需求 | 按时完成 |
| --- | --- | --- | ---: | ---: | ---: |
| 额度刚好覆盖现在和后续需求 | 普通 / 4 | 无 | 0 | 12 / 12 | 12 |
| 资源充足，近期截止紧迫 | Fast / 7 | 无 | 0 | 14 / 14 | 14 |
| 关闭预测 | 普通 / 4 | 无 | 0 | 15 / 20 | 15 |
| 同状态，85% 概率两小时后刷新 | 普通 / 4 | 无 | 0 | 19.25 / 20 | 19.25 |
| 同预测，100% 重视最差情景 | 普通 / 4 | 无 | 0 | 15 / 20 | 15 |
| 额度耗尽，一小时后刷新，任务可等待 | 等待 / 0 | 无 | 0 | 8 / 8 | 8 |
| 同余额，任务一小时内截止，愿意为速度付费 | Fast / 7 | 无 | 49 | 8 / 8 | 7 |
| 额度耗尽，有备用 reset，两小时内截止 | Fast / 7 | 现在兑换 | 0 | 12 / 12 | 11 |
| 同需求与余额，没有备用 reset | 普通 / 4 | 无 | 32 | 8 / 12 | 8 |
| reset 半小时后到期 | 普通 / 4 | 现在兑换 | 0 | 8 / 8 | 8 |
| 同状态，reset 两天后到期 | 普通 / 4 | 保留 | 0 | 8 / 8 | 8 |

## 观察

1. 普通 / Fast、reset、credits 的建议会随资源和需求共同变化，不是只由剩余百分比触发。
2. 预测开启不必改变第一段动作。本组参数下改变的是后续计划和期望完成量；未发生情景仍只完成 15 单位，不会把 19.25 的期望数写成保证。
3. 截止与库存价值会冲突。有 reset 的例子中，计划完成 12 单位但只按时完成 11，体现当前评分宁可留更多资源，也不为最后 1 单位继续使用较贵的 Fast。这是需要用户用真实偏好判断是否接受的结果。
4. `risk=100` 只优化最差情景，收益更好的情景可能被保守动作限制。真实 reset 到来后需重新优化；当前没有在计划内部实现自适应情景树。

## 测试发现并修复

最初给未到期 reset 的期末价值打折，产生了“在任务结束后兑换 reset，仅因资产形态变化就获得更高评分”的现象。改为把仍有效 reset 的可恢复容量合并入库存后再取双窗口瓶颈；同一状态下两天后到期的 reset 现在会保留。

根据实际要试算的输入方式，备用 reset 改为每张仅恢复周额度一次。表单按到期日录入，同一天最多一张；测试覆盖重复日期和兑换后不恢复短时额度。

## 当前结论

核心搜索和资源模拟可以运行；两段小问题与穷举分数一致。11 个构造场景能验证若干合理行为，也暴露了效用权重和保守计划的取舍。另见 `sweep-results.md` 的 480 组后台数据扫测、`local-prediction.md` 的合成试算及 `public-backtest.md` 的公开事件历史回放。仍没有真实账户状态与任务需求的策略回放，不能据此宣称比人工策略节省多少、或最优决策率是多少。
